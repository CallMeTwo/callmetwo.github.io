title: Reproducible workflows
summary: Structure data, code, software, and analysis decisions so statistical results can be rerun, reviewed, and updated reliably.

## Overview

A reproducible analysis is one in which another analyst can trace how raw inputs became reported results and rerun the workflow in a documented computational environment. It is a scientific quality practice: transparent transformations expose errors, preserve analytic decisions, and make updates less fragile. Reproducibility does not guarantee validity; the same code can consistently implement a biased design. It makes the work inspectable.

The minimum useful record includes data provenance, immutable raw data where permitted, versioned analysis code, software and package versions, a data dictionary, and a clear route from code to tables and figures. For sensitive health data, reproducibility may require controlled access rather than public release; code, synthetic examples, and a data-access statement can still make the analysis auditable.

## Organize a project around inputs and outputs

Separate raw, processed, and derived data. Treat raw data as read-only and never overwrite it during cleaning. Store scripts or functions that transform raw inputs into analysis datasets, then scripts that fit models and create outputs. Keep generated results separate from hand-edited narrative. A simple project might use:

```text
project/
  data-raw/       # source extracts; access controlled
  data-derived/   # generated by scripts, usually not committed
  R/              # reusable functions
  scripts/        # ordered analysis steps
  reports/        # Quarto/R Markdown source
  renv.lock       # package versions
  README.md       # instructions and data provenance
```

The exact layout can vary; the rule is that a reader knows which files are inputs, which are generated, and what command rebuilds the analysis. Use relative paths rooted at the project rather than paths tied to one computer. Avoid scripts that depend on an undocumented working directory, manually opened spreadsheets, or hidden objects from an interactive session.

## Use explicit, testable transformations

Data cleaning should be encoded as named steps: validate identifiers, parse dates, recode categories, derive outcomes, and check ranges. Keep source variables where possible and create derived fields with clear names. Do not silently drop records. Log exclusions with reasons and summarize counts at each step. Assertions can stop a pipeline if assumptions fail:

```r
library(dplyr)
stopifnot(!anyDuplicated(raw$id))
analysis <- raw |>
  mutate(event = as.integer(outcome_code == "event"),
         followup_days = as.numeric(end_date - index_date)) |>
  filter(eligible == 1)
stopifnot(all(analysis$followup_days >= 0, na.rm = TRUE))
```

This is illustrative: coding of event and eligibility must come from the study protocol, not be inferred from field names. Assertions should reflect valid data constraints; overly strict checks can reject legitimate edge cases. Add checks for missingness, permitted categories, impossible date ordering, and expected counts.

Use functions for repeated operations and avoid copy-pasted analytic logic. Parameterize input locations and study options in one place. Set random seeds for stochastic operations such as bootstrap, imputation, or cross-validation; record the generator and seed. A seed supports repeatability for the same code and environment, but changes in parallel processing or software versions can still alter results.

## Version control decisions and code

Git records changes to code, documentation, and small non-sensitive files. Commit coherent changes with messages that explain why; do not commit credentials, identifiers, or confidential datasets. A `.gitignore` should exclude temporary files, caches, and generated outputs when those can be recreated. Tag important releases or record the commit hash associated with a manuscript and archived outputs.

Version control is most useful when analysis code is modular and reviewable. Prefer small functions with explicit inputs and outputs over a single long notebook with hidden state. A notebook can be an effective report if it runs from a clean session top to bottom. Restart the R session and render the document as a check for hidden dependencies, but do not treat successful execution as proof the analysis is correct.

For team work, use branches or pull requests to review changes to endpoint definitions, cohort construction, and model formulas. High-impact derivations can receive independent review. Record decisions in the repository rather than relying on email or memory. If data corrections arrive, retain the old extract, identify the new version, and rerun all downstream steps from source.

## Lock the computational environment

Statistical software packages change. Record R version, operating system where relevant, package versions, and external software dependencies. `renv` can capture an R library state in a lockfile; containers can preserve more of the system environment. A lockfile is a snapshot, not a guarantee that packages remain available forever. Archive the code and dependencies according to institutional policy.

```r
install.packages("renv")
renv::init()
# After installing project packages and confirming the analysis:
renv::snapshot()
# A collaborator restores the recorded package environment with:
renv::restore()
```

Do not update every package automatically immediately before submission. Test upgrades deliberately, review behavior changes, and record the version used for final results. For numerical reproducibility across hardware, exact bitwise equality may not be realistic for parallel or floating-point algorithms; define reasonable tolerances and explain material differences.

## Generate reports from code

Use Quarto or R Markdown to combine methods, code, tables, and figures in a document rendered from a clean session. Tables should be generated from the same analysis objects used in the results, not copied by hand. Avoid embedding private data in rendered HTML or notebook outputs. For restricted data, clear outputs before committing and provide a controlled rerun path.

Dynamic reports reduce transcription errors but introduce their own risks: cached chunks may be stale; code can suppress warnings; and results may be inadvertently altered by manual edits. Disable or carefully manage caching for data-sensitive analyses. Include a header with project, data version, code commit, run date, analyst, and intended use. Save session information with final outputs.

## Reproducible example: analysis from data to estimate

The workflow below imports a source file, validates core fields, derives a binary outcome, estimates a difference in risk, and reports group denominators. The resulting table can be rendered automatically. Real projects should add provenance, missingness handling, design-aware standard errors, and tests for expected data structure.

```r
library(readr)
library(dplyr)

raw <- read_csv("data-raw/trial.csv", show_col_types = FALSE)
stopifnot(all(c("id", "arm", "event_code") %in% names(raw)))
stopifnot(!anyDuplicated(raw$id))

dat <- raw |>
  mutate(event = as.integer(event_code == "READMIT"),
         arm = factor(arm, levels = c("control", "active")))

summary <- dat |>
  group_by(arm) |>
  summarise(n = n(), events = sum(event), risk = mean(event),
            .groups = "drop")
summary
```

The derivation is valid only if every participant has complete 90-day outcome ascertainment and `READMIT` is the prespecified outcome code. If some outcomes are unknown, converting missing event codes into zero is wrong; preserve missing status and use the planned missing-data method. A reproducible pipeline makes that issue visible and gives a reviewer one place to inspect outcome derivation.

## Quality checks and independent review

Reproducibility supports verification. Compare derived counts with a trusted source, inspect distributions, check duplicate IDs, validate joins, and confirm event totals against adjudication. Unit tests are useful for deterministic helper functions, such as time-to-event derivations or recoding rules. Integration checks verify that the full pipeline produces expected outputs from a small fixture dataset. Tests should focus on code behavior and not be mistaken for statistical validation.

Code review should ask whether the implementation matches the SAP, whether factor reference levels are correct, whether missing values are treated intentionally, and whether standard errors respect clustering and design. Check model warnings and failed resamples. Independent reproduction of a primary result can catch coding errors that package tests cannot. Preserve a record of changes arising from review.

## Data privacy, access, and sharing

Health data often cannot be made public. Follow consent, law, ethics approval, data-use agreements, and institutional security rules. Remove direct identifiers and assess re-identification risk before sharing any derived data. A public repository can contain analysis code, data dictionaries, synthetic data, and instructions without exposing patient records. A secure enclave or controlled-access application may allow authorized users to rerun analyses.

Synthetic data should be clearly labeled and should preserve only the features needed to demonstrate code behavior. It does not validate scientific conclusions or substitute for access to original data. State who can request access, what approvals are required, and whether the data can be reused. Never include secrets or patient identifiers in code, commit history, logs, or screenshots.

## Rebuilding a cohort without hidden state

Cohort construction is often the most consequential and least visible part of a biomedical analysis. Write it as a pipeline with explicit inclusion dates, eligibility conditions, index-date logic, follow-up windows, and exclusion reasons. Preserve one row per intended analysis unit and validate that joins have not duplicated participants. A flow table generated from the pipeline should show counts after each exclusion and final outcome availability.

Avoid opaque spreadsheet transformations. If an external data extract arrives with renamed fields or corrected records, store the raw version securely and record a checksum, receipt date, and change note. Scripts should operate on a named version rather than a mutable “latest” file. Where raw data cannot be committed, provide a mock schema and synthetic fixture to exercise code paths without disclosing individuals.

An analysis dataset should not be assembled by editing a file by hand between script steps. Derive every variable programmatically and record the rule in code and a data dictionary. For clinical endpoints, document adjudication status, event date, censoring date, and competing events. For survey or registry data, preserve weights and design variables through transformations. Reproducibility begins with a stable definition of who and what the rows represent.

## A practical record for stochastic analyses

Bootstrap, multiple imputation, Bayesian sampling, and cross-validation use randomness. Set seeds close to the operation and record the number of replicates, chains, folds, or imputations. For parallel computation, record the parallel backend and random-number stream strategy; a single seed may not guarantee identical results under a different scheduling order. Save enough diagnostics to show Monte Carlo error is negligible for the reported quantity.

Do not save only the final random output while losing the code that created it. Preserve the model formula, tuning parameters, prior specification, and data version. When rerunning a stochastic process produces small numerical differences, compare estimates relative to their Monte Carlo and sampling uncertainty. A result that changes its scientific conclusion across seeds indicates insufficient simulation precision or instability and should be investigated.

## Reports, notebooks, and rendered artifacts

Interactive notebooks encourage exploration, but hidden state can make them misleading. Before finalizing, restart the session and run every cell in order; remove unused exploratory chunks or mark them clearly. A clean report should fail loudly if required data are missing or a model does not converge. Warnings should be reviewed and summarized rather than globally suppressed.

Keep the source document and rendered artifact together or archive both with their relationship documented. Record the renderer and package versions, input data version, code commit, and run timestamp in the report. A PDF or HTML file is useful for readers but cannot replace source code. If rendered outputs contain confidential information, apply the same access controls as the underlying data.

Tables and figures should be generated from named objects and saved with reproducible commands. Avoid copying estimates into a separate spreadsheet or manuscript by hand; automated reporting can insert values directly. Review each output after rendering for units, labels, denominators, reference groups, and rounding. Reproducibility can prevent transcription errors but cannot judge whether a displayed estimate answers the intended question.

## Environment choices and long-term access

`renv` is appropriate for many R projects. Use it after package installation and snapshot a known working environment. For operating-system libraries or external tools, a container such as Docker can add detail, but containers require maintenance, security review, and a strategy for archival. Choose the simplest environment that captures dependencies relevant to the analysis. Record system requirements when a package relies on external libraries.

Long-term reproduction can fail because package repositories disappear, APIs change, licenses expire, or data-use permissions end. Archive source code and lockfiles in a durable institutional repository; where allowed, preserve source packages or containers. Do not assume a public Git repository will preserve a controlled dataset or that a container guarantees data access. Include a maintenance contact and state what parts of the workflow can no longer be rerun.

## Team roles and review checkpoints

Assign responsibility for data provenance, cohort derivation, statistical code, and final report generation. Analysts should agree on a versioned analysis dataset and avoid parallel copies with ambiguous names. A second analyst can review the design-to-code mapping, independently reproduce key counts, and verify the primary estimate. Document review findings and resolutions.

For collaborative projects, code review should happen before the final report, not only after errors are suspected. Pull requests create a readable history and make changes easier to discuss. A reviewer should be able to run the pipeline or inspect a restricted reproducibility log. Keep issue tracking for known limitations, planned updates, and data anomalies; do not rely on private notes that disappear when staff change.

## Limits of reproducibility claims

An analysis is computationally reproducible when another authorized analyst can regenerate its outputs under specified conditions. That statement does not imply that the data represent the target population, the model assumptions hold, or the causal interpretation is valid. A perfectly reproducible biased estimate is still biased. Pair computational transparency with design appraisal, sensitivity analysis, and independent scientific scrutiny.

Open data are not always ethical or legal, and public code may expose security vulnerabilities or proprietary methods. Explain constraints rather than implying that a lack of public data makes the study irreproducible. A controlled-access pathway, synthetic test fixture, executable code, and detailed variable definitions can substantially support verification while protecting participants.

## A concrete run protocol

A README can give a short sequence such as: obtain authorized data extract version 2026-09-15; place it in the approved secure input directory; run `renv::restore()`; execute `Rscript scripts/01_build_cohort.R`; execute `Rscript scripts/02_primary_analysis.R`; render `reports/main.qmd`; compare output row counts with the expected validation record. Commands should be tested on a clean environment and should stop if data do not match the documented schema. Never place restricted extracts in a public repository just to make the example executable.

For each release, retain a compact manifest containing input identifiers or checksums, extraction date, code commit, software environment, execution command, completion status, warnings, and output locations. This makes it possible to distinguish a change caused by new data from one caused by code or package updates. A manifest should avoid storing protected information; it can identify a dataset version without exposing row-level data.

## Tests for analysis code

Unit tests can check that a helper function correctly derives follow-up time, classifies an event window, or handles a missing date. Fixture-based tests can verify expected cohort counts from a small synthetic dataset. Integration tests can run the full pipeline on that fixture and compare key outputs within a tolerance. For stochastic algorithms, test invariants and broad expected properties rather than requiring exact random draws across all package versions.

Tests should correspond to domain rules. An assertion that all ages fall between 0 and 120 might detect data errors but should allow the protocol's actual eligibility range. A test that locks in an arbitrary count without documenting its derivation can become an obstacle after legitimate data corrections. Keep expected values tied to an independently verified source and update them only with an explanation.

The workflow should surface warnings, missing categories, empty groups, and failed model fits. Capture session information and package versions with final results. These practices make it easier to determine whether a rerun difference is a genuine analytic change, a data revision, or numerical variability.

Finally, preserve enough project context for staff turnover: identify the data steward, statistical lead, repository location, access request process, and expected maintenance period. A reproducible project is a maintained research artifact, not merely a folder that once ran on one computer.

When a workflow depends on manual adjudication, document the adjudication form, reviewer instructions, and how disagreements were resolved. Human decisions are part of the pipeline even when they cannot be reduced to deterministic code. Preserve an audit trail while protecting identifiable data, and version the rules used to convert judgments into analysis variables.

Record changes to adjudication guidance over time and identify which dataset version used each rule.

Preserve version history for code and data derivations.

Record which versions generated each published result.

Reproducible workflows

A result you cannot re-derive is a claim, not a result. A reproducible workflow records the data, the code, the environment, and the settings — so the same analysis, re-run by anyone on any machine, gives back the same numbers. That is what makes silent errors discoverable.

Core idea & motivation

A statistical workflow is reproducible when, given the same data, the same code, the same documented environment (language and package versions), and the same settings — including any random seed — anyone, including the original analyst six months later on a different machine, can re-run the analysis and obtain identical results. The claim is about results from the same inputs, and it is a property of the workflow, not of the analyst. (Background: the overview of reproducible research on Wikipedia ↗.)

Why invest in this? Because a point estimate with no way to re-derive it is a claim, not a result. A 2016 survey of more than 1,500 scientists found that a substantial share could not reproduce another scientist's experiments and an even larger share could not reproduce their own — the so-called reproducibility crisis (Baker 2016). And the problem is not only that we cannot re-derive results: much of what is published is false or over-stated in the first place, and reproducibility is one of the tools that keeps us honest about which findings survive scrutiny (Ioannidis 2005).

  • Trust in published estimates. Reproducibility is what makes an estimate checkable — the difference between "trust me" and "here is the exact chain that produces it."
  • Error detection. Silent mistakes — a typo in a variable name, a stale CSV, an undocumented cleaning rule — change results with no obvious trace. A reproducible pipeline makes the discrepancy systematically discoverable (see the worked example, where the same raw export yields two different effect sizes depending on whether the cleaning rule is applied).
  • Meta-analysis inputs. Pooled estimates are only as good as the component studies' numbers; if a component estimate cannot be reproduced, the meta-analysis inherits an unquantifiable uncertainty.
  • Regulatory / HTA scrutiny. Reviewers increasingly request code and data access, or at minimum documented methods plus provenance, for submissions and health-technology assessments.
  • The cost of "which version did I run?" Without version control the question is unanswerable — and an unanswerable question is where analyses die.
The punchline: reproducibility is not a philosophical stance, it is error control. It converts "I think the answer was −13.1" into "here is the exact chain of operations that produces −13.1, and here is how you can verify it."

Reproducibility vs replicability

These two words are often used interchangeably, but the standard distinction is precise and worth teaching explicitly (the literature uses the terms loosely; we follow the NASEM-style convention, and flag where usage varies):

  • Reproducibility — same data + same code + same environment → same numerical results. You are checking the pipeline: does the same analysis, re-run, give back the same numbers?
  • Replicability — an independent group repeats the study — new participants, new measurements, sometimes a new setting — and reaches the same scientific conclusion. You are checking the inference: does the effect hold up under independent re-investigation?

A study can be perfectly reproducible (everyone re-derives the same point estimate from the same data) and still fail to replicate (a second cohort gives a different estimate). Peng (2011) makes exactly this distinction for computational science: reproducibility is about being able to arrive at the same answer from the same inputs with the same documented procedure; replication is about whether the scientific conclusion holds when the inputs change.

In health research the distinction is not pedantry. A regulatory or HTA reviewer who asks "can we reproduce your number?" needs code + data + environment + seed. A meta-analyst who asks "will your effect replicate in other populations?" needs study quality, generalizability, and — for the meta-analysis — your input estimates, which must themselves have come from a reproducible pipeline. Confusing the two leads to asking the wrong question of the wrong reviewer.

The pieces of a reproducible pipeline

This is the central section. A reproducible workflow is a small set of components working together; each one exists because something specific breaks without it. The list below follows the "best practices for scientific computing" framing of Wilson et al. (2014) — a concise, domain-agnostic checklist that has become the de-facto standard.

Version control for code (git)

Every commit is a dated, named, attributable snapshot of the entire project (code + config + data-processing scripts). (Version control on Wikipedia ↗) You can answer "what was the code that produced the submitted table?" exactly, diff between versions, and roll back a bad change. By convention, main holds the pipeline that produced the current report, and a tag (e.g. v1.0-submission) marks the exact commit behind a published or submitted analysis — the tag is the reproducibility contract.

What breaks without it: the final.R, final2.R, final_REAL.R, final_FINAL_use_this.R zoo. With no dated snapshots you cannot say which file produced which number, and "final_REAL" is a guess. Reproducibility dies at the filename.

Single entry point: the pipeline should have one command that runs everything — one script, or better a Makefile target (make report) or an renv-aware driver that calls the stages in fixed order. One entry point means "re-run" has one definition, and it is what you put in the README.

Code organization

One stage per script, scripts in a fixed order, intermediate artifacts in a known place. A small concrete layout (R-flavored; identical in substance for Python):

sbp-reg/
├── data/
│   ├── raw/        # the original export, IMMUTABLE (git-ignored or checksummed)
│   │   └── sbpreg_raw_export_2025-01-14.csv
│   └── clean/      # derived, regenerated from raw on every run
├── code/
│   ├── 00_setup.R      # load env, set seeds, define paths
│   ├── 01_clean.R      # raw -> clean (documented rules)
│   ├── 02_analyze.R    # stats: means, SD, diff, bootstrap
│   └── 03_report.R     # knit/compile the report from 01+02
├── results/    # generated tables/figures — OUTPUTS, never hand-edited
├── report/sbp-reg.Rmd  # narrative + code + outputs, one document
├── renv.lock           # pinned R package environment
└── README.md           # how to rebuild everything

What breaks without it: ad-hoc scripts scattered across home directories that load "the" data file from wherever it last happened to be; no way to know whether 02_analyze.R is reading raw or clean data; a colleague cannot follow the order.

Environment management / dependency pinning

The analysis depends on the language and the packages — not just your script. Your .R file is one input; the R version and every loaded package's version are inputs too.

  • R: renv creates a project-local library plus a renv.lock recording exact package versions, sources, and hashes (packrat is the older equivalent).
  • Python: requirements.txt (or pip freeze / poetry.lock / uv.lock for exact pins) inside a venv, or conda with an environment.yml.

The principle: record what you used, install that — not "latest." renv::restore() / pip install -r requirements.txt reconstructs the recorded environment; install.packages("everything") does not. A minor package version change can silently change a default (an algorithm flag, a tie-handling rule, a plotting default) or even a numeric result (a patched numerical routine, a new BLAS path). The script hasn't changed; the machine's libraries have. Pinning is what makes the environment part of the artifact (Peng 2011).

Data versioning & provenance

Data files change out from under code — the CSV in your inbox is not the CSV in your folder three weeks later. Record the exact source (who sent it, export timestamp, the database query if it came from one) and a file checksum (e.g. SHA-256) so the file you analyze is verifiably the file you documented. Keep raw data immutable; write derived/clean copies to a separate location — cleaning code reads raw and writes clean, never edits raw in place. A data dictionary / README describes variables, units, coding, and every cleaning rule (with the reason).

When data cannot be shared (privacy): you still document the provenance fully — source, version, checksum, transformation chain — and, where possible, release a synthetic exemplar that exercises the same pipeline.

Randomness & seeds

Any randomness in the pipeline — bootstrap/simulation resamples, train/test splits, "random" figure jitter or layout — must use a documented seed set at a known point (convention: the top of 00_setup, before any random draw). Same seed + same RNG + same algorithm + same package version → same draws → same numbers. An undocumented seed (or worse, no seed) means the result cannot be reproduced even with perfect code — the re-run is a different experiment. And the seed alone is not enough: the RNG algorithm and its implementation (package/version) must also be pinned, because the same seed through different RNGs gives different streams.

Generated artifacts & report generation

Tables, figures, and plots are OUTPUTS of code, never hand-edited in Excel or an image editor. A manually moved data label is a fork in the pipeline that no re-run can fix. Regenerate from raw data on every run; if the figure changes, the change is in the code or data and is therefore traceable.

Report generation — R Markdown / Quarto / Jupyter — keeps code + narrative + outputs in one document that re-renders reproducibly: chunks can echo the code, print the package versions, set the seed, and every displayed table and figure is rebuilt on re-knit. The report is then a generated artifact too, with the same guarantees.

Documentation

A README that another person can actually follow to rebuild everything: the data source + version (and checksum), the environment install command (e.g. renv::restore() or pip install -r requirements.txt), the single run command (e.g. make report / Rscript code/run_all.R), and the expected outputs — what files appear and what the headline numbers should be, so the re-runner can verify their re-run against yours. The test is the rebuild test: can a stranger, following only the README, reproduce the report?

Automation (CI) as the final check

A scheduled or pull-triggered build that re-runs the whole pipeline on a clean machine — GitHub Actions, a cron job, or a fresh container — catches environment and dependency drift early (a package update breaks renv::restore() or changes a result) instead of letting it surface at submission time. Keep this as the final check: it verifies the pipeline still runs; it does not make the pipeline reproducible by itself (Wilson et al. 2014).

Worked example: the SBP-Reg registry study

The scenario (clearly illustrative)

"SBP-Reg" is a made-up small registry study: 40 patients, 2 arms (20 control, C-01…C-20; 20 treatment, T-01…T-20); outcome = change in systolic BP from baseline (mmHg; negative = reduction). The raw export arrived by email and contains three transcription slips — a physiologically impossible one-off value in each case, corrected against the source case-report form by a single documented cleaning rule. All numbers below were recomputed in code and match the pinned values exactly.

The data, and the three slips

Clean (corrected) control, in ID order: 2, 5, 8, 3, 11, 6, 4, 9, 14, 7, 5, 12, 2, 8, 10, 3, 6, 13, 4, 9

Clean (corrected) treatment, in ID order: -6, -3, -8, -5, -11, -2, -4, -7, -9, -13, -3, -5, -8, -2, -6, -10, -4, -7, -3, -5

The raw export is identical except for three slips:

  • C-09 (control, position 9) recorded 144 instead of 14,
  • T-10 (treatment, position 10) recorded −130 instead of −13,
  • T-16 (treatment, position 16) recorded −103 instead of −10.

The documented cleaning rule — "a physiologically impossible one-off value, corrected against the source case-report form" — fixes exactly these three and restores the clean values.

The two-sample standard error of the mean difference, the t statistic, and the large-sample (normal-approximation) 95% confidence interval are:

SE = √( s12/n1 + s22/n2 )   ·   t = θ̂ / SE   ·   95% CI ≈ θ̂ ± 1.96 · SE

Plugging in the clean means and SDs (n1 = n2 = 20) gives SE = 1.069, t = −13.10 / 1.069 ≈ −12.259, and a normal-approx CI of (−15.194, −11.006).

So the raw export makes the treatment look 2.30× more effective than it is (−30.10 vs −13.10 mmHg). The three impossible values also inflate the arm variances, so the raw-data standard error balloons to about 10.4 and any inference built on it is nonsense — but the point estimate is what a colleague would report if they simply ran the analysis on the email file.

Bootstrap of the mean difference

A stratified bootstrap (resample within each arm, recompute the difference, repeat) gives a percentile 95% confidence interval. For B replicates, the interval is taken from the percentile points of the B bootstrap differences:

95% CI = ( θ̂[⌈0.025·B⌉], θ̂[⌈0.975·B⌉] )  ·  θ̂[j] = j-th smallest of the B bootstrap differences

With a fixed seed (42) and B = 1000 on the clean data the percentile 95% CI is [−15.100, −11.100] around the estimate −13.10 — tight and well inside the normal-approx interval. On the raw data the same seed and B give an estimate of −30.10 with a CI of [−50.500, −12.250]: the impossible values inject huge resampling variance, so the interval is wildly wider and its lower end is physiologically absurd. The teaching point (stated explicitly): without a documented pipeline — a documented data source (which export, when), documented cleaning rules (the three impossible values and the rule that corrects them), version-controlled code, and a documented seed — a colleague re-running the analysis six months later from the raw email export reports −30.10 mmHg, and there is no systematic way to discover the discrepancy against the "real" −13.10. The two numbers differ by 2.30×, and only the existence of the cleaning rule (documented, in code, applied from immutable raw data) makes the three slips detectable and the corrected result −13.10 defensible. The pipeline — not the person's memory — is what makes the difference. That is the whole argument for reproducibility in one example: the error was real, silent, and large; and it was caught by structure, not by luck.

Common confusions

  • Reproducibility vs replicability. Reproducibility = same data + code + environment → same results (a claim about the pipeline). Replicability = independent study, new data → same conclusion (a claim about the science). One can hold without the other (see above).
  • "Working" vs reproducible. "It runs on my machine" is not "another person can run it." Working = the author's local environment happens to contain the right versions and files. Reproducible = the environment, data, code, and seed are recorded and installable/runnable by anyone. Most analyses that "work" fail the second test.
  • Reproducibility vs open science. Open data is not sufficient — you still need the code, the pinned environment, and the documentation. Conversely, a fully documented but closed pipeline (private data, shared code + provenance + synthetic exemplar) can be reproducible in substance. Openness and reproducibility overlap, but neither implies the other.
  • A random seed vs a deterministic pipeline. The seed makes randomness reproducible; it is not the same as having no randomness. A seeded bootstrap is still a resampling experiment — the seed just means the re-run draws the same resamples. And the seed only helps if the RNG + package version are also pinned.
  • Version-controlling code vs versioning data. Code in git = dated snapshots of your work. Data needs its own provenance record (source, timestamp/query, checksum, cleaning rules) because data is usually not something you author and commit — it arrives from elsewhere, changes without your commits, and (when private) may never enter git at all.

Assumptions & limitations

  1. Reproducibility ≠ correctness. A pipeline reproduces exactly whatever its inputs and assumptions produce. A wrong model, or a cleaning rule that drops the right patients, can be perfectly reproducible and still wrong. Reproducibility is error control (you can find and see the mistake); it is not error prevention.
  2. Environment drift can survive pinning. Even a perfect lockfile doesn't pin the OS, the BLAS / linear-algebra library, CPU/FPU details, or floating-point ordering in parallel code — sources of tiny nondeterminism that can flip last digits (usually harmless, occasionally not, e.g. when sorting tied values or choosing convergence paths). Document the OS, and note that "identical to the last digit" may legitimately mean "identical to ~15 digits."
  3. Private data cannot be fully released. Mitigations, in decreasing order of strength: full documentation of provenance + cleaning rules; a synthetic exemplar that runs the same pipeline; code-only release with a data dictionary. None restores full verifiability — which is exactly why the provenance record matters when the data itself can't travel.
  4. Effort cost is real; "minimum viable" is a prioritization. The pragmatic ordering: (1) code in git, (2) a documented seed, (3) a README a stranger can follow — before anything else; full lockfiles + CI for anything you publish or submit. Treating reproducibility as an all-or-nothing project is the fastest way to get none of it.

Practical takeaways

The minimum viable reproducible setup — do these before anything else, and add the rest as you publish or submit (Wilson et al. 2014):

  1. Put all code in git. Dated, named snapshots; tag the commit behind each submission (v1.0-submission). Kill the final_FINAL.R habit.
  2. Pin and record the environment. renv (R) / requirements.txt + venv or environment.yml (Python). Record the language version too. Install what you used, not "latest."
  3. Keep raw data immutable and document every cleaning rule. Raw in, clean out; provenance = source + export timestamp/query + checksum; a data dictionary with units and codings.
  4. Set and document the seed at a known point, before any random draw — and note the RNG/package version it applies to.
  5. Generate every artifact from code. No hand-edited Excel tables or retouched figures; regenerate from raw on each run.
  6. Use report generation (R Markdown / Quarto / Jupyter) so code + narrative + outputs re-render together from one document.
  7. Write a README a stranger can follow: data source + version, environment install command, the single run command, expected outputs. Re-run the whole pipeline before every publication/submission (ideally on a clean machine, via CI), and confirm the headline numbers match the report.
